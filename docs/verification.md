# Verification

`chipleap verify DIR` checks a design bundle with open-source tools. Each step is skipped, with the reason, when its tool is missing, so a laptop with only Python still gets the consistency check and a full EDA setup gets everything.

```text
$ chipleap verify out
consist PASS     design.yaml, RTL wrappers, driver, register map and X-HEEP configuration agree
lint    PASS     Verilator -Wall reports no warnings
sim     PASS     21 randomized jobs bit-exact; cycle model error 0.0% max without stalls, ...
synth   PASS     logic cell area ... mm2 on IHP SG13G2 (model ... mm2), critical path ... ns, about ... MHz
xheep   PASS     X-HEEP validated the configuration (... banks, ... interleaved) and rendered 27 templates
```

Results go to `DIR/verify/verify.json` and `DIR/verify/VERIFY.md`. Choose steps with `--steps consistency,lint,sim,cdc,synth,xheep`; place and route (`pnr`) takes many minutes, so it runs only when named, or with `--steps all`.

A bundle may come from someone else, so ChipLeap never writes through a symlink in it. `DIR` itself (like the directory you give `explore` and `generate` with `-o`) may not be a symlink, and neither may `verify/` or a step's directory in it (`verify/synth`, `verify/pnr`, `verify/genus` and so on): the run stops with an error that names it. A symlink further inside a step's directory is removed before the step writes there, and nothing it points at is touched. On Windows a directory junction, or any other reparse point, counts as a symlink. A directory that `-o` creates gets a `.chipleap` file that says ChipLeap made it, and ChipLeap never empties an output directory without one.

This page is about generated bundles. The same command verifies RTL you wrote, given a `project.yaml`: lint with Verilator and slang, your cocotb tests on Icarus or Verilator, coverage, formal proofs of your properties with SymbiYosys, clock and reset domain crossing checks, synthesis, equivalence of the RTL and its netlists, place and route with the signoff settings below, and your tests again on the routed netlist with SDF delays. [projects.md](projects.md) describes it.

## Consistency

A bundle gets edited by hand once it leaves ChipLeap. This step re-derives every generated value from `design.yaml` and reports each file that disagrees:

- the RTL wrappers' parameters (`chipleap_accel_top.sv`, `chipleap_accel_xheep.sv`),
- the driver's build constants and register offsets (`sw/chipleap_driver.h`),
- the register decode in `rtl/chipleap_accel.sv` and the reggen description `rtl/chipleap_accel.hjson`,
- the CPU, bus and banks in the X-HEEP configuration;
- for an accelerator on its own clock (`accel_mhz` in `design.yaml`), that both wrappers put it behind its crossings (`chipleap_accel_cdc`) and that `rtl/chipleap_accel_cdc.sv` is there, and for one on X-HEEP's clock that they do not;
- with external memory on X-HEEP, that both wrappers give the accelerator its direct read path (`EXT_DIRECT`) for the X-HEEP configuration's external window, with as many reads in flight as the memory's latency needs at its clock, and that `rtl/chipleap_mem.sv` is there; without, that they do not.

## Lint

`verilator --lint-only -Wall` on the accelerator with the design's parameters, and with external memory on X-HEEP on `chipleap_mem` too, with the design's ports and X-HEEP's three external slave ports. The test suite lints all three dataflows over a spread of shapes, including 1 x 1 arrays, and the memory block with one to four ports, on one clock and two, and expects no warnings at all.

## Simulation and the cycle cross-check

The bundle's Verilator testbench (`tb/tb_chipleap.cpp`) drives the accelerator through its register interface, exactly as firmware would: it includes the generated driver and calls `chipleap_plan`, `chipleap_start` and `chipleap_busy`. A memory model sits on the OBI ports. It grants each request unless a random stall is drawn, and answers a fixed number of cycles after the grant.

Each case fills memory with random int8 activations and int8, int4 or int2 weights packed as the hardware expects, runs one job, compares every output with a golden matrix multiply and reports the cycle count from the `CYCLES` register. The default cases cover decode-shaped GEMV, small GEMMs, edge tiles in every dimension, K tiling with non-resident activations, every weight format the PEs accept, and two cases with 30 % random stalls and three-cycle latency.

For each case, `simulate_job` in `chipleap.model.accel` predicts the cycle count from the same tile plan. On this release:

- every case on all three dataflows is bit-exact;
- without memory stalls the prediction equals the simulated count exactly;
- with random stalls it is within a few percent (the model uses the average grant rate, and waits for the slowest read port, since each port reads its own share of a transfer).

The closed form the explorer uses (`job_timing`) is within 0.1 % on average of `simulate_job` over random jobs; jobs of up to 256 tiles use `simulate_job` directly. Together this ties the explorer's numbers to the RTL.

Verilator models are cached by a hash of their sources, parameters and the Verilator that built them (its path and version) in `~/.cache/chipleap` (`CHIPLEAP_CACHE` moves it), so re-running costs seconds and another Verilator builds its own.

### The accelerator on its own clock

A design with `accel_mhz` runs the accelerator on a clock of its own, `accel_clk_i`, behind `chipleap_accel_cdc` (`rtl/chipleap_accel_cdc.sv`), whose other side has the accelerator's ports on X-HEEP's clock. Each signal crosses through one standard structure:

- the register interface through a two-phase request and acknowledge handshake: the bus side holds the request in registers and toggles a request bit, which reaches the accelerator through two flip-flops; the accelerator side captures the request when that bit changes, performs it, holds the response and toggles an acknowledge bit back the same way, and the bus sees `ready` once the response is captured on its side;
- each read port and the write port through two asynchronous FIFOs of eight words, one for the requests and one for the responses, their pointers gray coded through two flip-flops. The accelerator side grants a request only while fewer than eight are in flight, so the response FIFO always has room for what the bus returns (an OBI response cannot be held back), and the accelerator keeps as many reads outstanding per port;
- the interrupt registered in the accelerator's clock and then through two flip-flops;
- `rst_ni` asserted at once in both domains and released in each through its own reset synchronizer.

The simulation step then runs `tb/tb_chipleap_cdc.cpp` with two clocks: the register interface and the memory model on X-HEEP's side at the SoC's clock (the design's, or what X-HEEP's SoC meets after routing), the accelerator at `accel_mhz`, its first edge a third of its period after the bus clock's. Every job must be bit-exact. When a request crosses depends on where the two clocks' edges fall, so no count is cycle exact across clocks; the model's crossing term (`chipleap.model.accel.crossed`, [model.md](model.md#the-accelerators-own-clock)) is held to the simulation instead. The test suite runs four accelerators at five pairs of clocks (35 and 90 MHz either way round, 100 and 100 MHz half a period apart, 42.3 and 100, and an odd ratio). Without stalls every count is within 5.5 % of the model's, and with random stalls within 10 %. In the cases simulated with the accelerator's clock the slower, the counts matched the model's cycle for cycle.

The `cdc` step writes the same top as an RTL project, with the design's parameters and both clocks, under `DIR/verify/cdc/`, and runs ChipLeap's CDC and RDC checker on it ([projects.md](projects.md)). It must find every crossing synchronized. For the SmolLM2 example's GEMV 1 x 8 it accepts 18: the handshake's two toggles and the interrupt through synchronizers, the eight gray-coded FIFO pointers, the five fields the handshake carries, the response FIFO's word written straight into the activation and weight buffers, and the two reset synchronizers. The test suite also breaks the crossings on purpose, with the interrupt taken from the accelerator's gate unregistered and with a FIFO's empty flag compared with an unsynchronized pointer, and the checker must report each. On a design without `accel_mhz` the step is skipped: nothing crosses.

Place and route lays the accelerator out with its crossings (`chipleap_accel_cdc` as LibreLane's top, the macro build's banks inside it as `u_accel`, the band between the macro rows sized for the crossings too), on both clocks: X-HEEP's side at the SoC's clock and the accelerator at `accel_mhz`. ChipLeap writes the constraints (`chipleap.verify.pnr.two_clock_sdc`): both clocks, the ports timed against X-HEEP's as LibreLane's base SDC would, and the clocks asynchronous with each crossing bounded. In the OpenSTA LibreLane runs, `set_clock_groups -asynchronous` between the two clocks also drops a `set_max_delay` on the paths between them (the path is reported unconstrained), and `-datapath_only` is not a flag. So every path from one clock to the other gets `set_max_delay -ignore_clock_latency` at the faster clock's period, which is OpenSTA's bound on the data path alone and keeps the bits of a gray-coded pointer within a cycle of each other where they are sampled, and `set_false_path -hold`, since a hold check between unrelated clocks times nothing. Paths within each clock keep their setup and hold checks. The step reports each path group's worst slack: setup at the slow corner and hold at every corner for each clock, and for the crossings ("path delay"). LibreLane's signoff report lists the design's thousand worst paths, not each group's, so a group with none among them is reported as above the largest slack listed.

These layouts were routed this way with LibreLane 3.0.0.dev44, X-HEEP's side at 42.3 MHz (the model's SoC limit when they were laid out; 36.8 MHz since #20's evidence layout), with setup at the slow corner and hold at the fast one, its worst:

| Accelerator (one write port) | Accelerator clock | Core | Cells | Setup, accelerator | Setup, X-HEEP's side | Setup, crossings (bound) | Hold, accelerator / X-HEEP's side |
|---|---|---|---|---|---|---|---|
| SmolLM2's GEMV 1 x 8, 4 x 256x64 macros | 90 MHz | 1.444 mm2 at 58 % | 37,737 | +0.292 ns | +14.39 ns | +4.49 ns (11.111) | +0.058 / +0.102 ns |
| the same | 100 MHz | 1.444 mm2 at 58 % | 37,883 | +0.165 ns | +14.07 ns | +3.21 ns (10.0) | +0.028 / +0.102 ns |
| GEMV 1 x 8, two read ports, 16-word flop buffers | 90 MHz | 1.235 mm2 at 65 % | 47,649 | +0.801 ns | +14.84 ns | +5.01 ns (11.111) | +0.055 / +0.100 ns |
| the same | 100 MHz | 1.235 mm2 at 66 % | 47,853 | +0.358 ns | +14.79 ns | +3.90 ns (10.0) | +0.048 / +0.100 ns |

All four are DRC and LVS clean, antenna clean under OpenROAD's check and IHP's deck, with no slew or capacitance violations. The slowest crossing in each is a request FIFO's word to an output on X-HEEP's side (`wr_addr_o` or `rd_addr_o`), well inside its bound. The SmolLM2 build on one clock had a 1.196 mm2 core and 29,009 cells, with 0.685 ns of slack at 90 MHz under LibreLane's base SDC, which on 3.0.0.dev44 applies no derate; the two-clock constraints apply the PDK's 5 %, and the crossings add their cells.

### The direct path to external memory

With external memory on X-HEEP the accelerator reads it over a direct path of its own, beside X-HEEP's bus ([xheep.md](xheep.md#external-memory-the-accelerators-direct-path)). The simulation step then also runs `tb_chipleap_mem.cpp` (in ChipLeap's sources, not the bundle) on a top of the accelerator with its direct ports and `chipleap_mem`, the arbiters in front of the memory ports:

- an on-chip memory model on the accelerator's X-HEEP ports, as before, and a model of the memory controller on the memory ports, which grants a request unless a random stall is drawn, keeps any number in flight, and answers each in order a fixed number of cycles after its grant (60 ns plus 4 cycles at the accelerator's clock);
- the weights in external memory, so they stream over the direct path, and in two more cases the weights on chip and the activations in external memory too;
- X-HEEP's three external slave ports (the CPU's data port, the DMA's read and write ports) driven by traffic generators: an idle port starts a read, or a write with random byte enables, to a region of its own in external memory with a set chance each cycle, holds it until granted and waits for its response. Every read is checked against a shadow copy of the regions, which are compared with the memory after each job, so a lost write shows too;
- at the memory ports, every request the controller did not grant must be there the next cycle, unchanged (OBI).

Every job must be bit-exact, every X-HEEP access right, and no request dropped or changed before its grant. With X-HEEP's ports idle and no stalls, the count is the model's exactly, with the memory's latency at the accelerator's clock and the stream at a word per port per cycle; the step reports the most reads in flight at the first memory port and the largest model error of those cases. On the CI's example (the Llama 3.2 1B design at 1.2 GHz, 76 cycles of latency, 128 reads in flight per port) the counts match the model's and up to 76 reads are in flight.

The test suite runs it on three accelerators (the SmolLM2 example's GEMV 1 x 8, a GEMV 4 x 8 with two ports, an output-stationary 8 x 2 with four) at latencies of 4, 9 and 14 cycles: the counts equal the model's, with as many reads in flight as the latency. With X-HEEP's ports busy beside the stream (30 % and 100 % of cycles, with and without stalls) every access is right, the arbiter never gives the accelerator two grants in a row while an X-HEEP request waits, and an X-HEEP port waits at most five cycles for its grant without stalls: X-HEEP's other two ports first, the accelerator before each. With the buffers in SRAM macros the counts equal the flop buffers'. With the accelerator on its own clock at three pairs of clocks the memory ports run on the accelerator's clock, X-HEEP's side crosses into it, and without stalls or traffic the counts are within 5.5 % of the model's. The arbiter alone, against a memory that stalls and answers after up to 40 cycles, never sends a response to the wrong master or out of order, holds every request stable until its grant, lets a waiting master see at most N - 1 grants to the others, and gives masters that always ask equal shares.

With `accel_mhz` the `cdc` step checks the accelerator with its memory block (`chipleap_accel_mem`): the memory ports' inputs belong to the accelerator's clock and X-HEEP's ports to the bus's. For the SmolLM2 example it finds 22 crossings, each synchronized; the test suite also gives X-HEEP's crossing FIFOs one clock for both sides, and the checker must report the arbiter reading them unsynchronized. `--steps pnr` lays the accelerator out with its direct ports, which behind the crossings are timed against the accelerator's clock.

## Synthesis

The accelerator's logic is synthesized with Yosys against the IHP SG13G2 standard cells (typical corner, 1.2 V). The buffers become SRAM macros in silicon, and their area comes from the macro liberty files instead. So the design is synthesized twice with tiny buffers (8 and 16 words) and the area is extrapolated to zero buffer words. ABC maps the logic with Yosys's fast script, then buffers high-fanout nets and sizes gates, as placement and routing would; its static timing of that netlist plus the flop's clock-to-Q and setup estimate the clock. Without buffering, a control signal that drives a few hundred flops looks like a 5 ns gate and the estimate is several times too slow. ABC sizes for a 5 ns target, the 100 MHz the node allows with room for the slow corner and routing. On this release the accelerators synthesize to 189 to 268 MHz at the typical corner; what they meet after routing at the slow corner is in the next section. A 1 x 8 GEMV engine takes about 20 s; `CHIPLEAP_ABC_FULL=1` selects Yosys's default mapping script, which saves a few percent of area and takes many minutes on multiplier-heavy logic. Each run's Yosys log is kept in the work directory.

The step reports the measured logic cell area next to the model's estimate for the same design on SG13G2, so the model's error is visible every time. The Yosys in Ubuntu 24.04 (0.33) cannot read every SystemVerilog construct the RTL uses, so the source goes through [sv2v](https://github.com/zachjs/sv2v) when it is installed.

The liberty file is found under `PDK_ROOT`, `~/.volare`, `~/.ciel` or `~/.local/share/pdk`; `CHIPLEAP_LIBERTY` points at it directly.

## Place and route

`--steps pnr` hands the accelerator to [LibreLane](https://github.com/librelane/librelane), the open flow behind the Tiny Tapeout IHP shuttles: Yosys, OpenROAD for floorplan, placement, clock tree, routing and timing repair, OpenSTA at every corner, KLayout with IHP's own rule deck for design rules, and Netgen for layout versus schematic. The clock is the design's own on IHP SG13G2, or the node's 100 MHz limit for designs on other nodes. LibreLane optimises at its typical corner by default; ChipLeap points gate sizing, buffering, the clock tree and the repair after global routing at the slow corner (1.08 V, 125 C) instead, because that is where the design is signed off, and repairs hold at every corner. Global placement is driven by timing, as LibreLane 3.0.0.dev44 placed by default; 3.0.14 turned that off (`PL_TIMING_DRIVEN`). 3.0.14's repair after placement also no longer upsizes gates that break no limit, which 3.0.0.dev44's did: a 12 x 12 multiplier routed at 5.4 ns with no timing repair missed the slow corner by 0.624 ns on 3.0.0.dev44 (97 gates resized) and by 1.608 ns on 3.0.14 (none), and by 0.314 ns on 3.0.14 placed for timing. It also has the repairs leave 0.8 ns (after placement) and 1.6 ns (after global routing) of setup slack, because detailed routing took 0.7 to 1.6 ns of slack away from the global router's estimate in our runs and nothing repairs timing after it.

### LibreLane's version and PDK

ChipLeap starts the `librelane` command (`CHIPLEAP_LIBRELANE` names another), usually a wrapper script that runs LibreLane's container. It pins what that runs, so a result can be reproduced:

- **LibreLane 3.0.14**, the release Tiny Tapeout's GDS action uses. ChipLeap passes the image `ghcr.io/librelane/librelane:3.0.14` to the wrapper as `LIBRELANE_IMAGE`, asks the wrapper for its version with it, and checks that every run's `resolved.json` records that version: a wrapper that starts another LibreLane fails the run. `CHIPLEAP_LIBRELANE_IMAGE` names another image; set empty, the wrapper keeps its own. An installed LibreLane that is no wrapper runs as it is, its own version checked the same way. The configuration ChipLeap writes follows the version (3.0.14 needs global placement turned to timing and KLayout's DRC thread count passed as IHP's deck reads it), so a run never starts without one: when the command gives no version, or none within 20 seconds (a wrapper that starts an Apptainer image can take longer on a busy node), the version is the image's tag, and with no image named, or one whose tag is no version, the run stops and says to set `CHIPLEAP_LIBRELANE_IMAGE`.
- **The IHP-Open-PDK commit of the checkout** the chip step takes its IO cells, DRC and LVS from (`CHIPLEAP_IHP_PDK`, or the one the standard-cell liberty is in), not the commit the LibreLane release pins (3.0.14 pins c4b8b4e). The first place and route installs that commit with ciel into `~/.local/share/chipleap/librelane-pdk/<commit>` (under `XDG_DATA_HOME` when it is set), which downloads about 800 MB once. ChipLeap runs the `ciel` command (`CHIPLEAP_CIEL`), or the one in LibreLane's image through docker. Without a checkout the commit is 22f2a25, the one ChipLeap is tested with. LibreLane then runs on that root as it is (`--manual-pdk --pdk-root`), and the wrapper is told to mount its directory (`LIBRELANE_PDK_ROOT`). Every run checks that its `resolved.json` names a root of that commit.

The install takes a lock, so two runs never install at once, and goes into a temporary directory that is renamed into place only once it is checked. The root must link to the commit asked for, and eight of its files (the technology and cell LEFs, the cells' GDS and slow liberty, the IO LEF, IHP's LibreLane configuration and DRC deck) must be the checkout's own, byte for byte, or, without a checkout, match ChipLeap's record of them at 22f2a25. A failed or offline download is an error that gives the ciel command to run by hand; ChipLeap never falls back to the commit the LibreLane release pins. `CHIPLEAP_LIBRELANE_PDK_ROOT` names a PDK root of your own instead, used as it is. `chipleap doctor` shows the root, its commit, why that commit (the checkout's, or ChipLeap's pinned one without a checkout) and whether it is installed. To install it by hand:

```sh
ciel enable --pdk-root "$HOME/.local/share/chipleap/librelane-pdk/22f2a25f1734796de3debbbf29cf697cbbc54081" \
  --pdk-family ihp-sg13g2 22f2a25f1734796de3debbbf29cf697cbbc54081
```

LibreLane 3.0.0.dev44, which pins IHP-Open-PDK cb7daaa, cannot load the LibreLane configuration of 22f2a25: it uses LibreLane 3.0's names (`IO_PIN_H_LAYER`, a run mode in `KLAYOUT_DRC_OPTIONS`). LibreLane 3.0 also loads the pad library a PDK's configuration names (`PAD_LEFS` and the rest, which IHP's names at 22f2a25); the chip step clears those, since it brings its own IO views ([chips.md](chips.md)).

Moving from 3.0.0.dev44 on cb7daaa to 3.0.14 on 22f2a25 changes results in known ways. IHP's configuration builds the clock tree from `sg13g2_buf_16` (it was `sg13g2_buf_8`), which costs area and clock power. The accelerator's place and route, which takes LibreLane's own constraints, gets the PDK's 5 % timing derate: dev44's constraints compute it as `TIME_DERATING_CONSTRAINT / 100` with the value as the integer 5, which Tcl's integer division makes 0, and 3.0.14's divide by 100.0. ChipLeap's own constraints, for RTL projects and chips, divide by 100.0 on either. The resizer in 3.0.14 repairs fanout with smaller buffers and upsizes fewer cells. Its clock tree has about half as many leaf buffers, each driving up to 19 flip-flops, which signoff reports over the standard cells' `default_max_fanout` of 8 (reported, not failed; the SmolLM2 accelerator has 157 such leaves). IHP's newer rule deck flags the pin markers its SRAMs draw off the grid, which are reported apart (below).

### SRAM macros

When the IHP PDK ChipLeap uses is installed (`CHIPLEAP_IHP_PDK`, or the one its liberty is in) and the build can take them without a change to its schedule, the buffers in the layout are IHP's own SRAM macros at the design's sizes. A build can take them when it is GEMV, has one DMA read port and COLS of 4, 8 or 16: a chunk of COLS bytes is one word of a COLS-byte bank, each weight lane has a bank of its own, each slot of a double buffer has its own banks, and one DMA port writes at most one word a cycle, which a single-port macro takes. The RTL's `SRAM_BUF` reads each chunk's bank word a cycle before the chunk issues (the tile's first when the tile starts, each next one while the one before it issues), and the issue registers the word in the operand registers as it registers the flop buffers' read, so the schedule is the same. An IHP macro's clock to output is about half the clock period at the slow corner, so the word is never in series with the multipliers, and the address of the next chunk is kept in registers a cycle ahead (the row's next chunk, the next row's first), so no adder sits between an issue and the macros' enables: the RTL tests run each such build against the flop buffers and the model, cycle for cycle, stalls included, with a model of the macros' ports that stops if a bank is ever read and written in one cycle ([the cycle cross-check](#simulation-and-the-cycle-cross-check)). `chipleap.gen.banks` chooses the macros (the width that wastes fewest bits, then the fewest that hold the depth, then area) and writes the top that holds the core and every macro under a fixed name (`abuf_s0_m0`, `wbuf_s1_l0_m0`).

The floorplan is ChipLeap's: a row of macros along the top of the core, standing upright with their pins (all on the bottom edge) facing down, a mirrored row along the bottom with its pins facing up, and the logic in the band between, sized for the model's standard-cell area of the macro build at 45 % utilisation: the flop build's logic and the interface the core adds for its banks (`accel_logic_kge` and `accel_bank_kge`), which a floorplan sized from the flop build's logic alone left out (0.054 of 0.332 mm2 for the SmolLM2 accelerator). Each macro keeps a 10 um halo, sits under a whole VDD and VSS pair of the core's TopMetal2 stripes, and is powered by a macro grid (Metal5 straps across its Metal4 supply stripes, TopMetal1 stripes over them, joined to TopMetal2). A 30 um column of rows stays at the core's left edge: OpenROAD's core is the bounding box of the rows, and without the column the rows cut under full-width macro rows would leave the macros outside the core's power stripes. No pin goes on the stretch of the top or bottom edge that a row of macros covers, from its first macro's halo to its last's (LibreLane's `IO_EXCLUDE_PIN_REGION`, from ChipLeap's floorplan): left to itself, LibreLane's IO placer put read-data inputs there, and their nets reached the logic through the margin under the macros, up to about 400 um, and failed antenna checks (one in the GEMV 1 x 4 build on IHP's deck, two in a SmolLM2 build on OpenROAD's check). The pins go on the left and right edges and on the ends of the top and bottom edges the rows leave free. The macros' slow, typical and fast liberty time them at every corner, and their CDL makes them boxes with pins for LVS. Repair after global routing runs, and wire length is capped at 300 um, so long nets to the macros' pins get buffers (below). Placement and routing read their own constraints, `pnr.sdc`: LibreLane's own (`base.sdc`) with a design-wide slew limit of 0.3 ns, and signoff reads `signoff.sdc`, LibreLane's alone, with every cell's own limit. IHP's SRAMs allow 0.595 ns at their inputs at the slow corner, a quarter of the standard cells' 2.5 ns, and OpenROAD's `repair_design` holds a net to its driver's limit and the design's, not to its loads'. In the GEMV 1 x 4 build an address bit driven 190 um from an `o21ai_1` was estimated at 0.54 ns at the macro's pin, was left alone even with a 50 % slew margin, and came out of routing at 0.80 ns, its wire 45 to 60 % more capacitive than estimated: five such pins broke the macros' limit. Under the 0.3 ns limit repair buffers or resizes those drivers, and the routed build has no slew or capacitance violation, for 3.4 % more cells and 2 % more cell area. The step adds the macros and their area to its result and compares them with the model's buffers, the model's logic with LibreLane's synthesis, and the routed standard cells with that synthesis (`macro_um2`, `model_buffer_um2`, `synth_cell_um2`, `model_cell_error`, `pnr_cell_growth`).

The two rows must also leave a core at most four times as wide as tall (`chipleap.gen.banks.MAX_ASPECT`). The flattest that routed is the GEMV 2 x 8 build's, two rows of three 784 um macros in a core of 2444 x 658 um (3.7 to 1). The GEMV 1 x 16 build needs two 64 x 64 macros for each 16-byte bank word, eight with a double buffer, in two rows of four: a core of 3249 x 438 um (7.4 to 1), whose logic stretches along a band 270 um tall between the macros' 1,536 data and mask pins. At 45 % utilisation its global routing ended with 1,594 overflows across six layers, and at 35 % the repair after placement buffered 10,000 long wires and detailed placement failed. Such a build gets flop buffers before LibreLane starts, with the core's size in the reason, instead of failing an hour into the run.

Otherwise, or when the design sets `accel.buffers: flops`, the layout keeps 16-word flop buffers, as in synthesis, and the result says which condition failed. The model prices and times such a build as one the banks cannot take: its buffers as macros of 32-bit words, no banks' interface and no macro read in its clock.

On LibreLane 3.0.14 a layout with macros, the accelerator's or a project's, sets two things more. 3.0.14 puts a port's buffer at its pin, and over a row of macros the pins are farther from the band than the 100 um the legaliser may move a cell: in the SmolLM2 accelerator's layout the band starts 161 um from the pins, and 44 port buffers found no row (DPL-0036). So `PL_MAX_DISPLACEMENT_Y` is the distance from the die's edge across every macro row that reaches the core's edge, plus 50 um (`chipleap.macro.place.edge_reach_um`). And the repair after global routing fixes hold to 0.15 ns instead of LibreLane's 0.05: IHP's SRAMs ask for up to 0.20 ns of hold time at their inputs at the fast corner, and with the derate 3.0.14 applies, detailed routing took two of that layout's `A_REN` pins to -0.059 ns. The margin is a point tuned on the SmolLM2 accelerator at 100 MHz, not a general constant: 0.10 left those pins at -0.058 ns, and 0.20 missed setup at the slow corner by 0.164 ns.

At the limit ChipLeap stops LibreLane, every process it started and the containers it runs in, and the step fails with the limit in its summary. Ctrl-C, SIGTERM and SIGHUP stop them the same way, and so does the MCP server when a `verify_soc` call is cancelled or the server shuts down. A container counts as the run's only when it carries the label `chipleap.run=<run id>`, and no other container is touched. ChipLeap puts a `docker` first on LibreLane's PATH that adds the label to `docker run`; a wrapper script around `docker run` and LibreLane's own `--dockerized` mode both go through it. A launcher that calls docker by its full path can add `--label chipleap.run=$CHIPLEAP_RUN_ID` itself; LibreLane with `LIBRELANE_CONTAINER_ENGINE` set cannot, and its container is not stopped. One run at a time can use a work directory. LibreLane runs without a terminal, so `--dockerized` needs `--docker-no-tty`.

LibreLane runs in two parts in one run directory: up to detailed routing, then the rest. LibreLane writes `final/` at the end of each part, the first one's included, so before the second part ChipLeap moves the first part's `final/` to `final-routed/` beside it and marks the second part's start. Results are read only from a `final/` the second part wrote after that mark, with LibreLane exiting 0; a second part that stops or ends on an error fails the step as a run that did not finish, and worst slacks no timing analysis gives (not a number, minus infinity, or finite and beyond 10^6 ns) are refused; plus infinity is a group with no path, unless it is the design's worst setup slack, which means nothing was timed against its clock and fails the step. In two of them the router's patch lay almost wholly on the stub's own metal, so a larger minimum for the router would only grow a patch that adds nothing. Instead each shape under the minimum gets a rectangle at one end along its layer's direction, as wide as that end and long enough to reach 0.15 um2, where no other net's metal, power grid, pin or obstruction comes within the spacing rule plus 0.05 um. The patched DEF goes back into LibreLane through `OpenROAD.DEFtoODB`, and the rest of the flow, signoff included, runs on it. A shape with no room at either end fails the step and is named. `minarea/patches.txt` in the work directory lists the patches, and an ECO runs the same way.

### The whole SoC

`--steps soc` places and routes X-HEEP with the accelerator as one block, with every memory in IHP's SRAM macros. It runs only when named, and takes hours.

1. ChipLeap copies X-HEEP at the commit it pins (the X-HEEP step's checkout, or `--fetch-xheep`) into `DIR/verify/soc/x-heep/` and renders it there with X-HEEP's own generator, for the configuration ChipLeap writes from `design.yaml`: the bundle's copy is Python, and the generator runs it, so it is never used.
2. FuseSoC lists X-HEEP's sources for its ASIC synthesis target and runs X-HEEP's generators: the register files, and the boot ROM, which a RISC-V GCC compiles for RV32. X-HEEP's cores need its own FuseSoC; `scripts/install_fusesoc.sh` installs it at the commit X-HEEP pins, beside nothing else (`CHIPLEAP_FUSESOC`). Only the design's CPU is synthesized: the other CPUs' cores are left out, their packages kept, since the MCU imports them.
3. ChipLeap writes what X-HEEP leaves to a technology, for IHP SG13G2 (`chipleap.gen.soc`): the top, `chipleap_soc`, with the accelerator on X-HEEP's external ports as the datasheet tells an integrator (its read and write masters on the external crossbar, its registers on the external peripheral bus, its interrupt on the external peripheral interrupt) and every other port a chip brings out as ports of the block: the pads' signals of the peripherals the configuration has, the pad control bus, and, when the design has external memory, one memory port per accelerator read port. Behind those, `chipleap_mem` puts X-HEEP's ports to its external slave window that the model uses (the CPU's data port and the DMA's read and write ports) and the accelerator's direct read ports on the memory controller's ports ([xheep.md](xheep.md#external-memory-the-accelerators-direct-path)). The rest is tied off inside the top: the pins of the peripherals ChipLeap's configuration leaves out ([xheep.md](xheep.md)), and the external slave ports of the CPU's instruction port, the debug module and the DMA's address port, never granted, as X-HEEP ties a slave it lacks. On the SmolLM2 example that leaves 374 pins of 1,278 (582 with X-HEEP's three external slave ports in place of the one memory port), and LibreLane's synthesis 1.842 mm2 of standard cells where X-HEEP's default peripherals made 3.233 mm2; X-HEEP's `sram_wrapper` in IHP's macros of 32-bit words with a bit mask, since X-HEEP writes bytes and the one macro without a mask (8192 x 32) cannot; and X-HEEP's clock gates on IHP's integrated clock gate, `sg13g2_slgcp_1`. The accelerator's buffers are its macros, as in `--steps pnr`. IHP's macros each hold their own copy of IHP's library cells, so the layout and the LVS netlist get several definitions of one name; ChipLeap merges them only when the layouts and the netlists are the same ([chips.md](chips.md)), and checks that before LibreLane runs. On IHP-Open-PDK 22f2a25 the 1024 x 32 and the 256 x 64 share 72 cells, all the same; the 512 x 32 holds its own `RSC_IHPSG13_CDLYX1` (its outline on layer 235/4, where the other macros draw it on 189/4), so it goes into no SoC with another of IHP's SRAMs: a design that needs it beside another macro (2 KiB banks, which X-HEEP holds in the 512 x 32, with the accelerator's buffers) stops there. A port of X-HEEP's MCU the top does not know stops the step, so a different X-HEEP is not wired by guess.
4. LibreLane reads the SystemVerilog with Yosys's slang frontend and synthesizes it first; ChipLeap checks the synthesized netlist with Yosys's `check` (no combinational loop, no undriven wire) and sizes the floorplan for the standard cells synthesis made, and the same run goes on to the layout: the macros in a row along the top of the core and one along the bottom, under their macro grid, signed off as the accelerator is, at the slow corner, with IHP's antenna deck on the GDS (`chipleap.verify.antenna`, its report in `DIR/verify/soc/antenna/`). LibreLane's own check, of the RTL word by word before synthesis, only warns: X-HEEP's flash controller with its cache off leaves its cache state machine undriven, and its OpenTitan SPI hosts' alert inputs are unconnected.

Design rules are IHP's deck, run by ChipLeap on the GDS after LibreLane, as the chip step runs it, with LibreLane's own KLayout DRC off (`chipleap.verify.pnr.ihp_drc`, its reports and logs in `DIR/verify/soc/drc/`). Density and recommended rules are left out, as LibreLane checks a block and the chip step checks a chip, and the summary says so; the deck's extra rules (`rule_decks/sg13g2_maximal.drc`), which LibreLane's check leaves out, are in. KLayout in deep mode keeps about one CPU busy whatever its thread count, so the deck runs as many processes: `run_drc.py` runs the main deck's 37 tables up to 8 at once, and beside it the extra rules run in up to 8 parts, each a run of the deck's rules with only the derived layers they use (`chipleap.verify.maximal`); with fewer than 4 threads, or a deck not laid out as the split expects, the extra rules run whole. Each part must exit cleanly, log the deck's last line and print a count for every rule it runs, and its report must hold something exactly when a count is not 0; on IHP's 41 unit test layouts the 8 parts and the whole deck reported the same 44,081 items in 228 rules. On the GDS of the last 36 MHz layout below that missed (the same 12 macros), at 16 threads, the step's DRC took 1 h 37 min with KLayout 0.30.7 (5,820 s; 5,901 s with 0.30.4), where LibreLane 3.0.14's own KLayout DRC, the main deck alone at 8 threads, took 2 h 0 min (7,197 s) and LibreLane 3.0.0.dev44's 3 h 48 min. Two parts set its length: the metal1 table (1 h 25 min, 1 h 19 min of it in M1.e, Metal1 spacing beside wide lines) and the extra rules' part with the latch-up group (37 min deriving its layers, then 58 min in the group); every other table and part ended within 20 min. The processes held up to about 36 GiB together. The only markers were IHP's off-grid Metal1 pin markers inside the 12 SRAMs, set apart by the rule above; LibreLane's stream-out of the SoC renames the SRAMs' cells (two characters before each name, as `EA_RM_IHPSG13_1P_BLDRV`), and `run_drc.py`'s tables report the markers in the top cell, 8,192 points, so ChipLeap reads the GDS for the cells only the macros place and for each placed macro's outline (`chipleap.verify.drc.macro_layout`, 10 s for the SoC's 374 MB) and sets apart a marker in one of those cells or inside an outline. LibreLane 3.0.14's check reported the same markers as 32, in the renamed cells.

The step passes when setup and hold are met at every corner and the checks pass as for the accelerator (DRC, LVS, OpenROAD's antenna check and IHP's antenna deck clean, no slew or capacitance violation at any corner). The result lists the macros, compares their area with the model's banks and buffers, and the model's logic (CPU, X-HEEP's logic and bus, the accelerator) with LibreLane's synthesis, and reports what place and route adds. The model's memory interface (the external memory's controller and PHY) is not in the block. It gives the worst setup and hold slack at each corner LibreLane signed off at, the clock the SoC met or missed at the slow corner beside the model's limit for it ([model.md](model.md#the-socs-clock)), and the run time.

The clock is the design's, or `--soc-clock MHZ`. The constraints time `clk_i` at it, and JTAG and the SPI slave at 20 MHz, each asynchronous to the others, as X-HEEP's synchronizers treat them. X-HEEP's I2S clock is `clk_i` through the I2S's divider and clock gate, timed at its fastest; its word select and data leave on that clock's falling edge, and are held to leaving within the cycle, as the clock itself is, not to a budget against `clk_i`. X-HEEP gates its clock in many places, on IHP's one, weak integrated clock gate (one gate feeds the peripheral subsystem's 15,000 flip-flops). OpenROAD's CTS balances the ungated flip-flops against the gates' trees with chains of delay buffers, as it balances registers against macros. With that balancing or without it, about 34,000 endpoints miss hold after the clock tree at 45 MHz, most of them flip-flops that X-HEEP's flip-flop FIFOs connect straight to the next, and hold repair inserts about 41,000 delay cells. Two choices keep the trees fewer and whole: a gate X-HEEP marks not functional (the GPIO input stages' power-saving gates) passes the clock through, as the generic cell allows; and no buffer goes on an output port before the clock tree, since CTS skips a clock net that already has one, and the I2S clock leaves on `i2s_sck_o`. The accelerator's macros get a buffer beside their clock pin each, right after the clock tree (LibreLane's `Odb.InsertECOBuffers`): CTS hangs them and some of X-HEEP's clock gates on one net of its first level, a buffer at mid-die with millimetres of wire to the core's corners, where after routing their clock pins saw 0.66 to 0.76 ns against their 0.595 ns limit; no setting of LibreLane's CTS step gave them a buffer of their own, and nothing after it buffers a clock net. The repairs' setup margins, the estimated setup slack they keep after the clock tree and after global routing, depend on the LibreLane that runs. On 3.0.0.dev44 they are 6 and 5 ns: routing took 4 to 5 ns from what the global router's estimate showed on the SoC's long paths. From 3.0.14 on they are the accelerator's 0.8 and 1.6 ns. 3.0.14's estimate uses IHP's fit of the layers' RC, and on the SmolLM2 accelerator laid out on two clocks routing took at most 0.38 ns from it on any group of paths. Margins as large as dev44's also lock hold repair out of a faster clock, since OpenROAD's hold repair adds no delay that takes an endpoint's setup slack below the margin. With the accelerator at 90 MHz, almost every one of its paths has less than 5 ns, and in a dev44 layout three flip-flops of a DMA read port's phase counter, each feeding back to itself through two gates, missed hold by up to 0.043 ns at the fast corner. Hold after global routing keeps 0.2 ns. For a trial run, `CHIPLEAP_SOC_SETUP_MARGINS` (two numbers of ns, comma-separated) sets other setup margins and `CHIPLEAP_SOC_HOLD_MARGIN` (ns) another hold margin.

From LibreLane 3.0.14 on, a buffer (`sg13g2_buf_2`) also goes after each output bit of every SRAM macro, X-HEEP's banks' and the accelerator's, beside the pin, in the same step as the macros' clock-pin buffers. A macro's outputs run side by side for hundreds of um, and the global router's estimate, which the repairs work against, leaves out most of the coupling between them. In a 36 MHz dev44 layout the bank outputs carried a median 1.19 times and at most 2.39 times their estimate over the same wire length after routing, and one ended at 0.0687 pF against the macro's 0.064 pF. On 3.0.14 an accelerator's buffer output was estimated at 0.0297 pF and came out 0.0650 pF. A limit set on the macros' pins in the constraints is not applied to them, and a design-wide one would buffer every heavy net. With a buffer beside the pin, the macro drives a few um and the buffer the wire.

Two more kinds of buffer are for trial runs, named in `CHIPLEAP_SOC_BUFFERS` (comma-separated); #20's evidence layout below has neither.

- `gates`: a buffer after each of X-HEEP's clock gates, where placement put the gate, in the same step as the macros' clock-pin buffers. IHP's integrated clock gate is a weak cell, and drives the root of its tree 0.4 to 0.8 mm away, so the gated flip-flops get their clock 0.6 to 0.7 ns after the ungated ones at the slow corner, and DMA0's registers are the worst hold endpoints in every 40 and 36 MHz layout. Since placement decides where the gates are, the layout then stops after the clock tree, ChipLeap reads the gates' places from the DEF it left, and the run goes on from the buffers' step. At 36 MHz the SmolLM2 SoC passed with them too, with +0.429 ns of setup and +0.053 ns of hold, where the evidence has +0.627 and +0.070 ns.
- `bank-outputs`: on LibreLane 3.0.0.dev44, the buffers after the SRAM outputs that 3.0.14's layouts always have. With them and the gates' buffers the SmolLM2 SoC met timing at 36 MHz on dev44 (+1.271 ns of setup, +0.070 ns of hold), with one net over OpenROAD's antenna check after routing, a bank output's on Metal2 (ratio 1.27), routed without the second antenna repair.

`CHIPLEAP_PNR_TIMEOUT` bounds synthesis and the layout, each; for this step it is 24 hours unless set.

With `accel_mhz` the accelerator runs on its own clock in the SoC too: the top has a second clock port, `accel_clk_i`, the accelerator sits behind its crossings (`chipleap_accel_cdc`, its macro build inside as `u_accel.u_accel`, keeping eight reads in flight per port, as many as each crossing holds), and with external memory `chipleap_mem`'s memory ports run on `accel_clk_i`, X-HEEP's side crossing into it. LibreLane gets both clock ports, and ChipLeap's constraints time `accel_clk_i` at `accel_mhz` (at most 100 MHz on IHP SG13G2) and the memory ports against it, and bound every path between it and `clk` as the accelerator's own layout does (`set_max_delay -ignore_clock_latency` at the faster period, no hold check, and `accel_clk_i` in no `set_clock_groups`, which in OpenSTA drops those bounds); a later input or output delay on a port replaces an earlier one in OpenSTA, so the memory ports are timed against `accel_clk_i` alone. The step reports each clock's worst setup and hold slack and the crossings', as the accelerator's layout does.

The SmolLM2 example's SoC (CV32E20, the one-to-many bus, one 32 KiB bank of eight 1024 x 32 macros, the GEMV 1 x 8 accelerator with four 256 x 64 buffer macros), laid out with `--soc-clock 36` at 6d026c0, meets its clock at every corner: +0.627 ns of setup slack at the slow corner (about 36.8 MHz there, 56 MHz at the typical corner), +0.070 ns of hold slack at the fast corner, DRC, LVS, OpenROAD's antenna check and IHP's antenna deck clean, no slew or capacitance violation. Its core is 7.271 mm2 at 54 % utilisation with 181,167 cells; the run took 8.1 h on 32 cores, 3 h 51 min of it in LibreLane 3.0.0.dev44's KLayout DRC, which the step no longer runs (above). Five layouts before it missed, all DRC, LVS and antenna clean, each with four slew violations at the accelerator's macros' clock pins (which the buffers beside them now drive):

- 50 MHz, antenna repair with a 100 % margin and 10 iterations: setup by 3.629 ns at the slow corner (1,054 endpoints), hold by 0.050 ns (2 endpoints), one capacitance violation (a bank's `A_DOUT[7]`, 0.0657 pF against 0.064 pF).
- 50 MHz, the repairs' wire length at 150 um: setup by 4.699 ns (2,526 endpoints), hold met by 0.049 ns.
- 45 MHz, both: setup by 3.162 ns (1,102 endpoints), hold by 0.065 ns (7 endpoints).
- 40 MHz, with the settings of the next: setup by 1.030 ns (20 endpoints, -6.5 ns in all), hold met by 0.104 ns, one capacitance violation (a bank's `A_DOUT[7]`, 0.0651 pF). IHP's antenna deck clean.
- 36 MHz, the accelerator's setup margins and no clock-pin buffers: setup by 0.219 ns (11 endpoints), hold met by 0.006 ns. IHP's antenna deck clean.

The worst paths ran from cve2's instruction register across the bus into the accelerator's and the DMA's registers at 40 and 36 MHz, and into cve2's own controller in the first 50 MHz layout; in the other 50 MHz layout and at 45 MHz they ran from a bank into the accelerator's buffer macro ([model.md](model.md#the-socs-clock) explains what they carry).

## After place and route

RTL projects have five more steps, for what follows place and route in an industrial flow ([projects.md](projects.md#after-place-and-route) describes their sections and results). Each writes an OpenROAD script from the project and runs the `openroad` command on it, and reads OpenROAD's reports back; LibreLane does the routing and the signoff.

| Step | Engines | What it reports |
|---|---|---|
| `dft` | OpenROAD `scan_replace` and `execute_dft_plan`, Fault 0.9 with Quaigh, Icarus 13 | scan chains and their order, stuck-at coverage, `patterns.json` and STIL, a flush pattern and ATPG patterns simulated through the chains of the scan netlist and, once it is routed, of the routed one |
| `pnr` | LibreLane | with `dft.insert`, the scan-inserted netlist routed with the usual signoff |
| `eco` | OpenROAD on the routed DEF, LibreLane resumed before detailed routing | the changes, and timing, DRC, LVS and antenna before and after |
| `power` | Icarus 13 with the cell models and the project's cocotb tests, OpenROAD `read_vcd` and `report_power` | power per group at each corner, from the tests' activity and vectorless |
| `ir_drop` | OpenROAD PDNSim (`analyze_power_grid`) | worst and average drop per supply net, the worst cells, a map |
| `upf` | OpenROAD `read_upf`, floorplan and placement on a hierarchical netlist | power domains, their cells inside their areas, the signals between domains |

Two OpenROAD builds take part, the `openroad` command and the one inside LibreLane's container, and they never exchange their databases: DEF, Verilog, SPEF and SDC go between them. Every input is staged into the step's work directory, because a containerised `openroad` sees only that, and OpenROAD runs through the same launcher as LibreLane, so a time limit (`CHIPLEAP_OPENROAD_TIMEOUT`, one hour by default), Ctrl-C or a cancelled MCP call stops it and its container. Gate-level simulation of IHP's cells needs Icarus 13 or newer (`CHIPLEAP_GL_IVERILOG`; Icarus 12 leaves every flip-flop at X). `chipleap doctor` lists `openroad`, `iverilog-gl`, `fault` and `quaigh`.

What the open tools cannot do is said where it matters: no open simulator is power aware, so a UPF changes placement but not simulation; LibreLane routes one supply; IHP SG13G2's standard cells have no level shifters, isolation cells or power switches; ATPG is stuck-at only, without at-speed patterns or compression.

## X-HEEP

Given an X-HEEP checkout (`--xheep DIR`, `CHIPLEAP_XHEEP_DIR`, or `--fetch-xheep` to clone the tested commit into the cache), ChipLeap:

1. loads the generated configuration with X-HEEP's own `load_config`, then runs `build()` and `validate()`, the checks `make mcu-gen` runs;
2. renders all of X-HEEP's Mako templates for it (RTL packages, bus, memory subsystem, linker scripts, headers) into a scratch copy, so the checkout is never modified, and reads back the bank counts from the generated `core_v_mini_mcu_pkg.sv`.

X-HEEP configurations are Python, and X-HEEP's generator executes them. So this step checks the configuration ChipLeap generates from the bundle's `design.yaml`, in a temporary directory, and never runs the bundle's own `xheep/<name>.py`; it says so when that copy differs, and the consistency step reports how. Bundles from elsewhere can be verified without running their code. Design and spec names are limited to letters, digits, `_`, `.` and `-`, because they become file names and appear in the generated RTL, C and YAML.

This needs `hjson` and `mako` in the Python that runs ChipLeap: `pip install "chipleap[xheep]"`.

## The test suite

`pytest` runs everything above that the machine supports, plus model tests:

- the parameter counts of the twelve LLM presets against their model cards;
- the IHP SG13G2 SRAM fits against every macro's liberty data;
- tile plans that always fit the buffers;
- the C driver's `chipleap_plan` against the Python `plan_tiles` on 6,000 random shapes (compiled with the host C compiler), and the driver compiled for RV32IMC;
- explorer determinism, Pareto non-dominance and the example specs;
- the MCP server end to end over an in-process client, and a run-log replay.

Tests that need Verilator are marked `rtl` and skip themselves when it is missing; tests
that need a commercial simulator or synthesis tool on the path are marked `commercial`.
The RTL project tests (`tests/test_project_*.py`) skip themselves without cocotb, Icarus,
Verilator 5.036 or newer (for coverage), slang, Yosys, SymbiYosys and z3, EQY, Icarus 13
(for gate level) or LibreLane, whichever they need. Each verification check has a passing
and a failing case: SymbiYosys proves a FIFO's properties and finds the counterexample in a
broken one; CDC passes two- and three-flop synchronizers, a handshake and a FIFO with gray
pointers and flags a missing synchronizer, logic before one, binary pointers, an
unsynchronized asynchronous input and a reset domain crossing; equivalence proves the
counter's netlist equal to its RTL and catches one changed gate, with Yosys and with EQY;
the UART's cocotb tests pass on its routed netlist with SDF (from a real LibreLane run kept
in `tests/fixtures/uart_routed`, since CI cannot route) and fail with one gate changed.
`tests/test_tool_path.py` plants programs named like the tools in a project and puts `""`
and `.` on `PATH`, and checks that every step runs the real tools or skips.
The real runs of the implementation steps need OpenROAD, Fault, Quaigh and Icarus 13 and
run with `CHIPLEAP_RUN_IMPL=1` (seconds on the fixtures); the ECO tests place and route
first and run with `CHIPLEAP_RUN_PNR=1`.
